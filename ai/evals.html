AI evals, explained

2026-09-26

An eval is a test suite for a non-deterministic system: instead of asserting output == expected, you score a model's output against a rubric or reference across many cases, and track the resulting pass rate as you change the prompt, model, or pipeline.

The core idea

A normal unit test is deterministic: same input, same output, every time. An LLM (or a RAG pipeline, or an agent) is not — the same prompt can produce different wording, different reasoning paths, or an occasionally wrong answer, even with temperature set to 0 in practice.

So you can't write assert output == "expected string". Instead:

  • Build a set of representative test cases (the eval dataset)

  • Run each one through your system

  • Score each output against a rubric, reference answer, or set of criteria — not a strict string match

  • Aggregate the scores into a percentage or pass rate

That aggregate number is what you track over time, the same way you'd track test-suite pass rate — except here it tells you whether a prompt change, a model swap, or a new retrieval step made things better or worse.

Anatomy of an eval

Every eval, regardless of what's being tested, has the same five parts:

  1. Test dataset — inputs plus expected or ideal answers. This is the hardest part to get right; a weak dataset makes the whole eval meaningless.

  2. System under test — the prompt, RAG pipeline, or agent you're actually evaluating.

  3. Generated output — what the system returns for each input in the dataset.

  4. Evaluator (scorer) — the logic that judges each output: a rule (exact match, regex), a human rater, or another LLM acting as judge.

  5. Score and report — the scores aggregated into a single number (pass rate, average score) you can compare across runs.

The loop closes when the score tells you to change the prompt, swap the model, or fix the retrieval step, then rerun the same dataset to see if the number moved.

Types of evals

TypeHow it scoresGood forWeakness
Exact match / rule-basedString or regex match, JSON schema checkStructured output, classification, tool-call argumentsUseless for open-ended prose
Human evalA person rates each outputNuance, tone, correctness on hard casesSlow, expensive, doesn't scale
LLM-as-judgeA second LLM scores output against a rubricOpen-ended text at scale, cheap approximation of human evalJudge itself can be biased or wrong; needs its own validation
Benchmark evalPublic dataset with known answers (MMLU, HumanEval, etc.)Comparing raw model capabilityTests the model, not your specific application
Custom / product evalYour own dataset + rubric for your actual use caseThe only one that tells you if your system worksYou have to build and maintain it yourself

Most real projects end up using two or three of these together — for example rule-based checks for structure plus LLM-as-judge for quality.

Common metrics

MetricMeasuresTypical use
Accuracy / pass rate% of cases scored correctAny eval type, the top-line number
Exact match / F1Overlap with a reference answerClassification, extraction, QA
Faithfulness / hallucination rateWhether output is grounded in the retrieved contextRAG pipelines
Retrieval precision / recallWhether the right documents were retrieved at allRAG pipelines, upstream of faithfulness
Task success rateWhether the agent actually completed the goalAgents
Tool-call correctnessWhether the right tool was called with valid argumentsAgents, tool use
Latency, cost per callTime and $ per requestAny system, alongside quality

For your RAG and agent sessions specifically: faithfulness and retrieval precision matter more than plain accuracy, since a fluent-but-ungrounded answer is the main failure mode RAG is meant to prevent.

Getting started

  1. Take 10-20 real or realistic inputs from whatever you're prototyping (prompting, RAG, or the agent sessions coming up) — that's v0 of your dataset.

  2. For each, write down what a good answer looks like: a reference string, or a short rubric ("cites the source doc", "doesn't fabricate a number").

  3. Pick one scorer to start: exact match if output is structured, LLM-as-judge if it's open-ended prose.

  4. Run your current prompt/pipeline against all 10-20, score them, get a baseline percentage.

  5. Change one thing (prompt wording, retrieval top-k, model), rerun the same dataset, compare the number.

That five-step loop is the entire discipline — everything else (bigger datasets, better judges, CI integration) is refinement on top of it.

Tools worth a look once you're past the manual stage: promptfoo and DeepEval (open-source, run locally), Ragas (RAG-specific metrics), LangSmith and Braintrust (hosted, add tracing). This list moves fast — worth a quick search before picking one, rather than trusting names in a doc written today.
